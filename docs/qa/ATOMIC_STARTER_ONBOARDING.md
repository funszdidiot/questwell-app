# Atomic starter onboarding (C02)

Home previously inserted a starter quest and then updated onboarding_completed
in a separate request. A crash or failure between them left a quest on an
unfinished profile, and retry created another. Skip also lacked the starter
button's in-flight guard.

The new `finish_onboarding_once` RPC takes the expected owner and one of the
three existing starter keys, or null to skip. It checks owner, active session
and deletion fence, then locks the caller's profile row. Creating the approved
starter, recording a private per-account outcome and completing the profile
are one transaction. Retries, including after app restart or from another
device, return the first outcome. No client-selected rewards or task IDs are
accepted. The three quest titles, difficulty levels and rewards are unchanged.

The private result persists after quest deletion and profile-flag resets, so
neither can issue another starter through this RPC. It cascades with Auth
deletion. Only the private definer can access it; the public wrapper is an
invoker with authenticated-only execution. Existing column grants remain intact.

## Legacy partial setup

Old quests have no reliable starter-origin marker. When an unfinished profile
has any existing quest or reward history but no durable onboarding result, a
starter request returns `needs_confirmation` without changing data. The welcome
panel asks the owner to finish setup with their current progress; that explicit
skip completes onboarding without inserting a quest. It does not guess from
titles, adopt personal quests, delete duplicates or rewrite rewards/history.
Users can create another normal quest later through the board.

Already-completed legacy profiles receive a durable completed-without-new-quest
result on their first RPC call. A legacy deleted, unpaid quest with no remaining
history cannot be identified; there is no retrospective reconstruction claim.

## Client behavior and tests

The existing welcome panel is extracted only to test this boundary. Starter and
skip share a synchronous guard, with all actions disabled while pending.
Failures remain visible and retryable. The service captures the owner and checks
it before sending and after receiving. A disposed panel cannot apply a late UI
callback. The existing cosmetic read/write coordinator prevents stale profile
loads overtaking onboarding. No state-management package or art changes.

Tests were authored before implementation. The isolated harness first records
the old path's failed one-quest assertion after a crash between its two writes.
It then applies the CLI-generated migration and exercises real Auth/REST:
all three starters, lost response, repeated calls/remount, concurrent different
choices/skip, legacy completed/partial/history-only states, deleted quests,
reset flags, ownership, anonymous/revoked/fenced callers and invalid input.
Forced task and profile write failures must roll back task, private receipt
and flag together. SQL checks cover grants/RLS; CI runs lint/advisors and the
existing reward, deletion and C01 suites. Session/widget tests cover transport
failure, duplicate taps, account switches, confirmation and disposal.

Local isolation/catalog tests pass (19). New Dart files are formatted; unrelated
existing formatting is preserved. Final CI/review evidence is recorded in the
PR and FIX_PLAN; this document does not predeclare pending checks as passing.

## Rollout and rollback

Source proposal and disposable GitHub-hosted synthetic tests only. Migration
`20261006013437_atomic_starter_onboarding.sql` was generated by the verified
Supabase CLI 2.119.0. Live rollout still needs separate G3 approval and migration
history reconciliation. The root migration chain remains blocked.

Apply the approved RPC before releasing a connected updated client. Missing RPC
fails closed without falling back to the two-write sequence. Older clients can
still use that sequence and remain unsafe, including races with updated clients;
rollout must retire the old starter path. This PR does not claim to fix it through
unchanged legacy grants. Roll back the client first, retain durable outcomes,
and do not restore/reset onboarding data or remove receipts as a routine rollback.
No historical duplicates, balances, live policies or hosted data are changed.
