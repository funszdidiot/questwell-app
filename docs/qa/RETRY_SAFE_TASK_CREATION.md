# Retry-safe quest creation (C01)

The New Quest form previously inserted a fresh row after every unconfirmed
write. Its button guard prevented simultaneous taps but not a retry after an
accepted response was lost. C01 gives each form submission a UUID, captures its
owner and original payload, and sends `create_task_once` on each manual retry.

The private transaction records `(user_id, request_id)` alongside a SHA-256
payload fingerprint and a server-generated task ID. A concurrent duplicate
waits on the unique key, then receives the original ID. Different content with
the same identity is rejected. The receipt survives task deletion, so a retry
cannot resurrect a completed/deleted quest. It contains no quest text and is
removed when its Auth owner is deleted. Clients cannot read or modify receipts
or choose task IDs. The existing task reward mapping remains authoritative.

Both the client and server compare the captured account with the current
account. The server additionally checks the session and existing deletion fence.
The new private definer is necessary to access the private receipt and assign
the protected task ID; its public wrapper is an invoker. Both have empty search
paths and explicit authenticated-only execute grants.

After an unconfirmed submission, the form retains its title/difficulty and
locks changes to that payload. The user can retry it or leave to check the
board. Exit copy acknowledges that the quest might already exist. Editing an
existing quest and preview callbacks retain their existing paths.

## Verification

Tests were written before the implementation. The disposable CI harness first
uses the existing direct-insert path and discards an accepted response. It
requires two resulting rows and records the failed one-row assertion as the
baseline red characterization. After the additive migration, real Auth/REST
tests cover lost-response retry, eight concurrent requests, intentional identical
quests with different keys, payload mismatch, deleted/completed tasks, account
switch, anonymous/revoked/fenced callers, invalid input and legacy inserts.
A forced downstream task constraint checks transaction rollback, including the
private receipt. SQL checks verify RLS, grants and protected task IDs.

Flutter tests cover stable retry identity, shared pending requests, account
switch during a response, changed-payload rejection, retained/locked form state,
honest navigation copy and successful retry. Existing double-tap/edit tests run
with the full suite. CI results are recorded in the PR; tests are not claimed
passing until that run completes. Local Node isolation/catalog checks pass (19).

## Scope, rollout and rollback

Only source and the disposable GitHub-hosted backend are authorized here. The
migration filename was generated by checksum-verified Supabase CLI 2.119.0.
Live deployment requires separate G3 approval and migration-history review;
the legacy root migration chain remains blocked. Apply the reviewed database
contract before releasing a connected client that uses it. A missing RPC fails
closed; the app does not fall back to the duplicate-prone insert path.

Older clients retain their existing INSERT grants and behavior, including their
existing duplicate risk. Starter onboarding, Chronicle repeat and boss creation
are separate planned concerns. No historical duplicates or balances are edited.
Form identity is in memory: closing/reopening the form or restarting the app
starts a new request. Durable offline drafts are outside C01; check the board
after abandoning an unconfirmed request. Roll back the client first and retain
the safe additive receipts; dropping them loses late-retry protection.

Official Supabase function/RPC documentation and the October 6 changelog index
were checked. No package or platform version changes are introduced.
